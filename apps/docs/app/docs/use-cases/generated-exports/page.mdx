# Generated exports

Nothing is uploaded by a user here: your server builds a CSV, a PDF or a ZIP and puts it in the
bucket. The body is already in memory, so `upload()` takes a string or a `Buffer` directly.

```ts
const rows = await db.order.findMany({ where: { organizationId } })
const csv = toCsv(rows)

const result = await bucket.upload(csv, {
  key: `exports/${organizationId}/${stamp}.csv`,
  contentType: 'text/csv',
  cacheControl: 'private, max-age=0',
})
```

A `string` body is encoded as UTF-8 and its content type defaults to `text/plain`, so pass
`contentType` explicitly for anything else. A key with an extension is enough on its own —
`.csv` is detected.

## Why store it at all

You could stream the CSV straight to the browser. Storing it buys three things:

- **A stable URL** you can email, or hand to a job that finishes after the request is gone.
- **A retry** that costs nothing: the export already exists, generating it again is optional.
- **A bounded request.** Generating a large report inside an HTTP request is what times out
  serverless functions; a background job that uploads when it is done does not.

## The background job shape

```ts
export async function runExport(jobId: string) {
  const job = await db.exportJob.update({ where: { id: jobId }, data: { status: 'running' } })

  try {
    const csv = await buildCsv(job)

    const result = await bucket.put(jobId, csv, {
      contentType: 'text/csv',
      filename: `orders-${job.createdAt.toISOString().slice(0, 10)}.csv`,
    })

    await db.exportJob.update({
      where: { id: jobId },
      data: { status: 'ready', size: result.size },
    })
  } catch (error) {
    await db.exportJob.update({ where: { id: jobId }, data: { status: 'failed' } })
    throw error
  }
}
```

The client polls the job, and once it reads `ready` it hits a download route that signs a URL:

```ts
const url = await bucket.getUrl(jobId, { expiresIn: 300, download: true })
```

`download: true` sets `Content-Disposition: attachment` without renaming the file; pass a string
when you want to control the filename the browser saves.

## Large exports

An export that outgrows your runtime's request limit cannot go through a single `PutObject` — see
[Size limits and streams](/docs/limits). Two options today:

- **Split it.** Write one object per chunk (`exports/<id>/part-001.csv`) and let the client
  download a manifest. Each part stays small, and a failed part is cheap to retry.
- **Use the SDK directly.** `@aws-sdk/lib-storage`'s `Upload` handles multipart over
  `bucket.client`, so it shares the same credentials and configuration:

```ts
import { Upload } from '@aws-sdk/lib-storage'

await new Upload({
  client: bucket.client,
  params: { Bucket: bucket.bucket, Key: 'exports/big.csv', Body: stream },
}).done()
```

bucketcode's own multipart support lands in v0.2, at which point the first form works without the
extra dependency.

## Cleaning up

Exports are the one kind of object that genuinely expires. Use an S3 lifecycle rule on the
`exports/` prefix rather than a cron job in your application — it is server-side, free, and does
not depend on your process being alive.
